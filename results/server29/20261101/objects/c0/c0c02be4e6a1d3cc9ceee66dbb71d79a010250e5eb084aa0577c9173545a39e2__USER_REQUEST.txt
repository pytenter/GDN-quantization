# Codex任务：Qwen/GDN历史OLD Runtime真实GPU恢复验证 V1

## 一、任务目标

任务名称：

`QWEN_GDN_HISTORICAL_RUNTIME_GPU_RECOVERY_V1`

目标模型：Qwen3.5-9B / GDN。

目标硬件：Qwen服务器，单张授权的RTX3090 24GB。

本任务承接已完成的：

`QWEN_GDN_HISTORICAL_RUNTIME_RESTORATION_V1`

**核心目标：通过最小GPU实验，确认已经完成CPU恢复的历史OLD Runtime是否能够重新达到约13 token/s，并判断其自身的数学正确性和可重复性。**

不要再次设计或优化Runtime。

### 需要回答的四个问题

1. 已恢复的OLD Runtime能否在真实9B模型上正确运行？
2. 同一张GPU上，两次fresh process执行的GDN state、logits和cache是否一致？
3. 在原历史128-token warmup + 128-token measurement窗口下，FP吞吐是否重新达到约13 TPS？
4. 如果恢复成功，是否可以将其作为后续Group32/INT8科研实验的运行协议候选？

注意：第四个问题仅评估协议可行性。本任务不运行Group32，也不自动授予INT8 GPU资格。

# 六、阶段C：OLD Runtime真实9B数值资格

这是本轮第一项GPU科学工作。

先只测试FP。

不得在这里混入Hadamard、Sym128、Group32或Dual-M。

## C1. 两次32-token fresh process

在同一张授权GPU上，分别启动两次独立Python进程。

两次必须使用：

- 同一模型。
- 同一模型权重。
- 同一输入token。
- 同一seed。
- 同一GPU UUID。
- 同一历史OLD Runtime。
- 同一dtype。
- 同一模型和Cache初始化方式。

每次从冻结的相同初始状态执行完整32-token真实模型forward。

保存：

1. 每token logits。
2. 全部GDN recurrent state。
3. 关键GDN计算中间状态。
4. Cache内容和元数据。
5. token/cursor身份。
6. 非finite检查。
7. 实际执行配置与依赖身份。
8. GPU运行及资源记录。

两条fresh轨迹应执行逐token、逐Tensor比较。

至少报告：

- `torch.equal`。
- byte equality。
- 最大绝对误差。
- 最大相对误差。
- 首次不一致token。
- 首次不一致layer/head。
- 不一致Tensor身份。

不能只比较最终token的logits。

### C2. 激活驱动FP64递推资格

按原冻结CPU任务预登记的数学合同，使用真实模型执行时记录的Key、Gate、Beta及相关更新输入，在独立CPU FP64参考路径中复核GDN递推。

要求：

- 真实激活必须来自当前执行。
- 不得使用随机生成的更新系数替代。
- 不得使用简化公式替换原数学定义。
- 不得事后修改已经冻结的数值容差。
- 原生GPU状态应与参考满足预登记的对应数值资格。

FP64参考是数学诊断，不表示GPU应与FP64逐字节相同。

如果真实GDN数学检查不通过，必须保存首个差异并停止性能资格。

### C3. 关于deterministic=False

历史OLD使用`deterministic=False`。

因此，需要特别警惕：

**OLD能正常运行，不意味着OLD自身可逐字节重复。**

如果两条fresh轨迹出现不一致：

- 保存最早分歧。
- 分析是否属于历史native计算的已知不确定性风险。
- 不直接放宽资格。
- 不自动改用NEW数值实现。
- 不因吞吐可能较快而授予正式科研资格。

如果本轮冻结的fresh一致性门禁失败，则停止可采用Runtime的性能晋级。

可以报告历史移植环境能运行，但不符合当前严格可重复科研使用要求。

# 九、阶段E：后续INT8科研适用性评估

本次只有FP GPU资格与吞吐恢复是主任务。

- OLD H首token不QDQ，历史窗口255次QDQ。

- FP32 Tensor中的post-QDQ数值不等于物理packed INT8。

这些协议差异不能忽略。

如果未来确实使用OLD移植协议研究Group32，则至少需要独立验证：

- H+C128 Sym。
- H+C32 Sym。
- H+C32 Asym。

这些实验必须使用相同的新冻结运行协议。

不得直接复用NEW_STRICT下的历史Future-KL，形成跨协议Codec因果比较。

特别注意：

即使FP达到13 TPS，也只能证明**本次历史移植Runtime在当前机器、当前窗口具有对应吞吐**。

它不证明历史完整二进制已精确复现，也不证明Group32 INT8具有13 TPS，更不证明所有长程数值路径合格。

---

# 十二、最终状态分类

使用以下分类：

- `HISTORICAL_PORT_FP_QUALIFIED_SPEED_RECOVERED`：当前9B FP数值资格PASS，三次短窗中位≥13 TPS。
- `HISTORICAL_PORT_FP_QUALIFIED_PARTIAL_SPEED`：FP数值PASS，但吞吐低于预设13 TPS目标。
- `FP_NUMERICAL_QUALIFICATION_FAIL`：GDN数学、cache、fresh重复性或安全数值门禁失败。
- `HISTORICAL_PORT_EXECUTION_FAIL`：移植环境无法合法运行。
- `GPU_RESOURCE_OR_IDENTITY_FAIL`：GPU UUID、Driver、依赖、监控或资源门禁失败。
- `PARTIAL_GPU_RESULTS_PRESERVED_AND_STOP`：部分执行合法完成，未满足完整终态资格。
- `CPU_ONLY_COMPLETE_GPU_NOT_AUTHORIZED`：未获得GPU授权，只有CPU资格交付。
- `FAIL_CLOSED_STOP`：触发禁止继续的前置或执行中门禁。

FP性能恢复成功时，还必须明确标记：

`INT8_GPU_QUALIFICATION=NOT_RUN`

不能将FP成功自动升级成正式Group32 Runtime。

# 十三、实际执行要求

请不要再生成一套泛泛的Runtime恢复计划。

前序CPU任务已经完成，现有控制修订也已经完成。

**本任务应直接消费前序CPU封存与最新修订，完成当前合法范围内的首次真实GPU恢复资格。**

执行顺序：

1. 定位并核验CPU交付及独立控制修订。
2. 核验407项有效源码和全部必要身份。
3. 建立全新独立执行root。
4. 读取GPU授权和permit。
5. 如果没有授权，完成CPU检查后STOP。
6. 如果已有独立有效授权，严格执行真实Driver设备映射门禁。
7. 通过后进行单GPU资源准入和NVML PID身份监控。
8. 两次fresh 32-token FP数值资格。
9. 激活驱动FP64递推资格。
10. 数值全部PASS后，运行最多三次128+128 OLD FP吞吐测量。
11. 预算允许时，补充一次NEW_STRICT短窗参考。
12. 完成INT8兼容性CPU审计，不运行INT8 GPU。
13. 形成完整的数值、性能、资源与科学决策。
14. SHA封存所有新任务交付。

### 明确禁止

- 修改历史OLD数学。
- 切换到其他GPU。
- 放宽fresh byte parity。
- 改变模型dtype。
- 修改GDN recurrent update。
- 使用新版数值实现伪装OLD。
- 自动运行H+C128或Group32。
- 自动开展32K/AIME。
- 修改旧封存或热更新控制器。
- 失败后不断修补/重试。
- 为达到13 TPS扩大GPU预算。

**最终目标不是进一步研究性能瓶颈，而是用一次严格、有限且可复核的GPU实验，判断你以前约13.7 TPS的Qwen/GDN运行能力是否已经在当前服务器上恢复，以及能否作为后续量化科研的Runtime基础。**
