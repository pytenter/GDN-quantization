# Codex科研任务：Qwen/GDN历史高吞吐Runtime的INT8 Group32接入与资格验证 V1

## 一、任务身份与目标

任务名称：

`QWEN_GDN_HISTORICAL_PORT_INT8_GROUP32_QUALIFICATION_V1`

模型：Qwen3.5-9B / GDN。

运行基础：已经获得FP短程数值资格和吞吐恢复的`HISTORICAL_PORT`。

### 核心目标

在不改变已恢复FP Runtime数学路径的前提下，实现并验证以下三个INT8实验条件：

| 编号 | Codec | 目的 |
|---|---|---|
| B0 | Key-H128 + C128 Sym | 建立匹配的原始量化基线 |
| B1 | Key-H128 + C32 Sym | 只检验Group Size 128→32 |
| B2 | Key-H128 + C32 Asym | 检验Group32下非对称量化的额外作用 |

本次不加入Dual-M、Permutation、Learned Rotation或其他新量化方法。

主要问题：

1. 恢复版Runtime能否正确执行真实INT8 persistent QDQ？
2. Group32 Sym能否保持GDN State更新及下一token读取语义？
3. Group32 Asym能否通过scale、zero-point、codes及状态写回资格？
4. 三种方法能否在完全相同的恢复版运行协议下公平比较？
5. 实际INT8吞吐是多少？相比历史OLD_H+C128是否存在明显额外开销？
6. 哪些条件已经具备进入32K Future-KL Pilot的资格？

**本任务的成功标准是数值和运行资格，不要求Group32提前证明Future-KL优于Group128。**

本次不启动正式32K、AIME26或Rotation训练。

# 四、阶段A：CPU-only恢复旧C128和Group32数学

## A1. 核验C128原始合同

优先找到：

- 已恢复HISTORICAL_PORT实际模型forward。
- 旧版Hadamard注入源码。
- 原C128 Sym Codec。
- GDN state QDQ/writeback。
- 原CPU数值fixture。
- 已有Qwen Group128/64 Asym CPU研究资产。
- 新历史移植Runtime有效源码清单。

首先确认实际State形状和量化轴。

按现有研究合同，GDN沿Key方向分组。

对于实际128×128 Key×Value State：

C128：

每个Value列中的128个Key元素共享量化参数。

C32：

每个Value列中的128个Key元素被划分为4个连续32元素组。

必须通过源码确认真实shape、layout和grouping，不得假设所有层都能按相同reshape直接处理。

### 元数据精度

此前Qwen canonical C128 Sym使用FP32 scale。

本次主实验建议统一：

`SCALE_DTYPE=FP32`

因此：

- B0使用原canonical C128的真实FP32 scale合同。
- B1采用同一FP32 scale精度。
- B2同样采用FP32 scale及整数zero-point。

不能将历史FP16 Group128/64 CPU实验中的数值直接当作本任务FP32匹配结果。

如果实际原C128源码与这里描述存在差异，以核验后的canonical实现为准，并在正式冻结前明确记录。

FP16 scale可作为后续独立敏感性实验，不进入本次主GPU矩阵。

## A2. B0：Sym128

严格复用原C128 Sym量化数学。

典型表达为：

\[
s_g=\frac{\max |X_g|}{127}
\]

\[
q=\operatorname{clip}(\operatorname{round}(X_g/s_g),-127,127)
\]

\[
\hat X=s_gq
\]

实际safe scale、rounding、dtype和clipping规则必须来自原源码。

B0不能因为接入新Runtime而改变Codec数学。

## A3. B1：Sym32

仅将每个Group包含的Key元素数量从128改成32。

其他规则与B0一致。

必须确认：

- 每个Value列产生4个Group。
- 不跨Value列共享scale。
- 不跨head或layer混Group。
- 每个Group独立计算FP32 scale。
- codes使用INT8。
- 重建后的State恢复原Key×Value布局。
- Hadamard坐标变换及逆变换正确。

## A4. B2：Asym32

每个32元素Group计算：

\[
a_g=\min(0,\min X_g)
\]

\[
b_g=\max(0,\max X_g)
\]

\[
s_g=\frac{b_g-a_g}{255}
\]

\[
z_g=\operatorname{clip}
\left(\operatorname{round}(-a_g/s_g),0,255\right)
\]

\[
q=\operatorname{clip}
\left(\operatorname{round}(X_g/s_g)+z_g,0,255\right)
\]

\[
\hat X=s_g(q-z_g)
\]

具体要求：

- UINT8 codes。
- FP32 scale。
- UINT8 zero-point。
- 减zero-point前转换为足够宽的有符号整数。
- 与Sym32保持相同Hadamard、分组方向和QDQ插入位置。
- 全零、常数、极小scale和边界情况采用冻结的明确规则。
- 不使用在线FP Oracle选择量化参数。

### 跨设备算术注意事项

此前Ling的Asym32出现过CPU/GPU标量除法与舍入路径不一致的问题。

本任务必须提前处理这一风险：

- 冻结scale、zero-point和code的运算顺序。
- 明确FP32除法及rounding实现语义。
- 独立保存CPU数学参考。
- GPU微型Codec资格优先于完整模型Canary。
- 如果CPU/GPU不一致，在首次数值失败时保存量化前输入及各阶段中间bits。

不能在发生差异后临时修改scale dtype、rounding或strict parity阈值。

如原Codec合同不足以保证指定的bit-level算术结果，应在科学评分前提出明确的新版本数值合同，而不是悄悄修改历史结果。

# 五、阶段B：冻结统一Persistent QDQ科学协议

这一阶段非常重要。

历史OLD与NEW的QDQ时序不同：

- 历史OLD H短窗口首token不执行QDQ，256 token窗口中有255次。
- NEW对应窗口从首token执行QDQ，共256次。
- 旧AIME又存在整段Prompt不量化Prefill的特殊协议。

**这些旧差异不能进入Group32的新匹配比较。**

## B1. 本次统一协议

建议新建：

`HISTORICAL_PORT_PERSISTENT_INT8_GROUP32_V1`

要求：

1. 使用已经恢复的HISTORICAL_PORT FP计算数学。
2. 对三种学生条件使用完全相同的模型输入和Hadamard。
3. 从冻结的第一个需要持久保存的recurrent更新开始执行QDQ。
4. 之后每个token、每个量化GDN state均QDQ并写回。
5. 下一token必须实际消费上一token的QDQ状态。
6. 不允许保留未量化State作为下一次更新输入。
7. B0/B1/B2的QDQ注入位置和时间必须一致。
8. 不得保留历史OLD首token漏QDQ行为并称其符合token0 persistent语义。

如果历史prefill采用多token chunk，必须确认其中每个token的state是否真正经历QDQ。

若不能在chunk内部逐token执行QDQ，应使用原生且数学合格的stepwise路径，或在资格阶段标记无法满足token0 persistent合同。

不能把chunk末尾单次QDQ冒充整段逐tokenQDQ。

### 注意

本协议可能与历史OLD_H+C128不完全一致。

这是允许的，因为本次建立的是独立匹配的INT8科研协议。

但必须确保：

**FP的历史数学路径不因新INT8适配而被修改。**

如果新协议的首tokenQDQ或逐tokenprefill方式改变INT8吞吐，必须如实计入新INT8运行成本。

## B2. Writeback资格

对于预冻结的layer/head/token：

必须核对：

- QDQ之前的State。
- INT8/UINT8 codes。
- scales及zero-points。
- QDQ重建后的State。
- 写入Cache的State。
- 下一次GDN kernel实际读取的initial_state。

尤其检查：

\[
S_{t+1}^{\mathrm{kernel\ input}}
=
\operatorname{writeback}(QDQ(S_t))
\]

这里的等价判定遵守实际Carrier dtype及冻结数值合同。

不能仅比较日志中两个对象指针，也不能用QDQ后State的hash代替下一kernel消费验证。
