## 一、任务目标

**TASK_ID：`QWEN_GDN_HISTORICAL_THROUGHPUT_RECONCILIATION_V1`**

你是我的Qwen/GDN推理系统与性能分析Agent。

此前在Qwen3.5-9B的AIME26实验中，记录的吞吐量约为：

| FP | 13.38 token/s |

5. CPU/PyTorch发射、同步及安全检查有何差异？
6. GPU硬件、软件环境、输入长度和Cache状态能否解释速度差异？
7. 在同GPU、同输入、同计时窗口下，旧路径是否仍然比新路径快？
8. 最终能否将差异定位到具体可验证的执行路径或测量因素？

**禁止没有证据就把速度下降归因于确定性模式、compensated cumsum、Column LS或CPU overhead。**

## 四、Phase 1：先核验历史吞吐的计算方式

CPU-only。

这是本任务最高优先级。

历史AIME runner可能使用：

```python
tokens_per_s = generated_tokens / latency
```

但最终报告里的13.38和9.12还可能是多个样本的统计汇总。

必须从原始记录重新计算，而不是直接相信历史汇总值。

针对FP和Hadamard分别计算：

### A. 每条生成的独立速度

\[
TPS_i=\frac{N_i}{T_i}
\]

### B. 所有样本TPS的算术平均

\[
TPS_{\mathrm{mean}}=\frac1n\sum_i TPS_i
\]

### C. 所有样本的中位TPS

\[
TPS_{\mathrm{median}}=\operatorname{median}(TPS_i)
\]

### D. 按总token数量与总时长计算

\[
TPS_{\mathrm{weighted}}=
\frac{\sum_i N_i}{\sum_i T_i}
\]

确认历史报告使用的到底是哪一种口径。

这些统计量不一定相等。

进一步检查每条记录：

- 是否完整成功
- 是否存在runtime error或nonfinite
- 是否因EOS提前结束
- 是否达到81920-token上限
- 是否包含Prefill
- 是否包含采样
- 是否包含输出解码或其他后处理
- 是否存在异常短样本
- 是否有多worker聚合混淆
- 是否存在GPU并发运行及争用

按输出长度分组，例如：

```text
0–2048
2048–8192
8192–32768
32768–81920
```

分析TPS与生成长度、Prefill长度、物理GPU的关系。

检查13.38及9.12是否可以从实际原始记录精确重算出来。

如果不能重算，必须明确报告：

`HISTORICAL_TPS_PROVENANCE_UNRESOLVED`

不能把历史数值当作已验证的基线。

输出：

`HISTORICAL_TPS_RECOMPUTATION.json`

`HISTORICAL_TPS_BY_LENGTH.csv`

`HISTORICAL_TPS_BY_GPU.csv`

## 五、Phase 2：执行路径差异的CPU-only审计

对FP和Hadamard分别进行。

不要将当前FP_NATIVE直接当作历史FP的同一实现。

建立如下对照表：

| 维度 | 历史AIME | 当前32K Profile | 是否同协议 |
|---|---|---|---|
| Model weights | 实际身份 | 实际身份 | 待核 |
| Torch版本 | 实际值 | 实际值 | 待核 |
| GDN kernel | 实际调用 | 实际调用 | 待核 |
| cumsum | 原路径 | 当前路径 | 待核 |
| deterministic | 实际值 | 实际值 | 待核 |
| TF32 | 实际值 | False | 待核 |
| Hadamard数学 | 原代码 | 当前代码 | 待核 |
| Quantization | 原协议 | 当前协议 | 待核 |
| Forward次数 | 实测/记录 | 实测/记录 | 待核 |
| 同步次数 | 实际源码 | 实际源码 | 待核 |
| 计时范围 | 原记录 | 新记录 | 待核 |

重点研究以下潜在差异。

### 2.1 Deterministic路径

确认历史AIME是否使用native cumsum及默认数值路径。

确认新32K实验的compensated cumsum和确定性处理实际应用于：

- Prefill
- Chunk Forward
- Recurrent Decode
- 全模型其它CUDA计算

**特别注意：不能因为新实验采用compensated chunk，就断言每token Decode都在反复执行这个补偿操作。**

必须找到实际调用链及执行证据。

如果差异只发生在Prefill，那么它无法直接作为128-token稳定Decode明显变慢的充分解释。

### 2.2 Kernel及模型主干

确认两套路径是否使用不同的：

- `torch_recurrent_gated_delta_rule`
- `torch_chunk_gated_delta_rule`
- GDN update实现
- Attention backend
- Linear、RMSNorm与其它ATen实现
- Tensor layout与dtype转换

查找是否存在：

- Python逐层循环
- 重复矩阵乘法
- 意外的FP32提升
- 新增安全检查
- 额外tensor复制
- CPU标量读取
- `cudaStreamSynchronize`
- `cudaEventSynchronize`

### 2.3 环境与硬件

检查：

- CUDA_VISIBLE_DEVICES与真实GPU UUID
- CUDA/PyTorch编译后端
- 是否使用相同的4090/3090/A800环境（不得仅按GPU编号判断）
- GPU clock、power limit及温度
- 其他GPU进程及资源竞争
- CPU型号、线程和负载
- 环境变量差异

从证据判断是否可能造成性能差异。

不要凭环境变量存在就声称其导致性能下降。

输出：

`PERFORMANCE_CAUSE_HYPOTHESES.md`

每项必须注明：

```text
OBSERVED
INFERRED
UNVERIFIED
RULED_OUT
```

并给出支持证据。

| 条件 | 历史runtime | 当前runtime |
|---|---|---|
| FP | OLD_FP | NEW_FP |
| Hadamard+C128 | OLD_H_C128 | NEW_H_C128 |

**FP组为Primary。**

理由是FP速度差异最大，而且不涉及Dual-M的额外量化数学。

Hadamard组为Secondary。

如果两套Hadamard的旋转位置、State表达、Prefill量化等语义不一致，应明确记录，不能强行称作数值等价对照。

所有测试必须使用真实对应runtime，而不是在当前runner中简单改变配置名称。

### 4.3 统一测试工作负载

使用同一组非AIME固定token序列。

优先复用既有冻结Doc1 token输入，核验其原始token SHA。

使用相同：


需要注意：

- 每个Trial独立重建Cache。
- 128-token warmup后，在同一Cache上继续计时128-token。
- 不允许重置Cache后假装继续Decode。
- 两套runtime都实际处理完整模型Forward。
- 必须核验每个token的Position ID和Cache增长。
- 必须核验GDN各层真实调用。
- 不能用空转循环或只执行部分层冒充完整Forward。

Primary使用固定token replay，排除采样导致的生成路径差异。

如果为了复现历史AIME吞吐定义，需要测采样/安全检查成本，可增加独立的辅助测量，但必须把采样结果与下一步固定输入解耦，确保Forward输入仍然一致。

### 4.4 测量方式

每个条件至少进行三次非Profiler测量。

采用平衡或交错运行顺序，尽量减少GPU温度、时钟和运行顺序造成的偏差；不要求同时加载两套9B模型。

计时要求：

- 计时窗口开始前同步。
- 计时窗口结束后同步。
- 中间不逐token增加全局同步。
- 不在Primary运行中启用Profiler。
- 不新增会改变原Forward执行的observer。
- 不计入模型首次加载。
- 不把JIT编译时间混入稳定Decode TPS。
- 保留完整wall time和实际token数。


各条件保留真实源码的数值设置。

如果历史路径 `deterministic=False`、当前路径 `deterministic=True`，允许将两条**原本不同的路径**用于性能归因，但必须注明它们不构成科学数值等价性证明。

禁止为了速度强行改变新32K科学路径的确定性规则。

### 4.5 辅助Profiler

只有在非Profiler结果显示旧新runtime存在稳定差异，且GPU预算仍充足时，才进行一轮有针对性的Profiler。

- Kernel launches/token
- `aten::mm` CPU self
- `cudaLaunchKernel` CPU self
- CPU同步与标量读取
- Forward CPU elapsed
- GPU kernel activity
- GPU active union
- Kernel调用种类差异


`wall - GPU active union`

## 八、Phase 5：针对真实差异做归因

根据实测结果，优先回答下面的判别问题。

### 结果1：旧runtime仍明显快于新runtime

例如同输入、同GPU、同窗口下：

```text
OLD_FP:  接近历史速度
NEW_FP:  接近7–8 token/s
```

说明执行路径差异可能是真实存在的。

此时应结合源码和Profiler定位：

- 哪一类Forward操作不同？
- 新路径增加了哪些Kernel？
- 新路径增加了哪些同步？
- 哪些差异发生在每token Decode，而不仅是Prefill？
- 哪些可能来自严格数值确定性？

尽可能给出有证据支持的耗时解释。

如需改变单项数值开关才能做进一步确认，必须将该测试列为独立诊断条件，不能作为原科学基线或正式加速结果。

不进行大规模代码修改。

### 结果2：两个runtime在同条件下速度接近

例如：

```text
OLD_FP ≈ NEW_FP ≈ 8 token/s
```

说明历史13.38很可能主要涉及测量工作负载、环境、版本或统计定义差异。

继续结合历史原始记录判断原因。

不能只因为旧runtime没有复现13.38就断言历史数据错误。

### 结果3：两套runtime都恢复到接近13 token/s

说明之前7.93的测量条件可能存在重要差异。

检查实际Forward次数、Cache、统计窗口、软件环境和GPU状态。

### 结果4：FP差异消失，但Hadamard差异仍存在

重点核验Hadamard实现：

- Q/K变换
- 旋转矩阵dtype
- H矩阵构建和缓存
- 转换调用频率
- Kernel dispatch
- State QDQ
- Prefill后量化
- 原始安全检查

不能把Hadamard的差异错误归因于Dual-M。

### 结果5：无法可靠归因

明确说明剩余差异和缺失证据，保持：

`UNRESOLVED`

不能为了得出结论而补造历史配置或调整阈值。

### 最终报告必须回答的8个问题

**Q1.** 历史13.38与9.12 token/s是否能够从原始记录重新计算？

**Q2.** 历史和新实验实际使用的吞吐统计口径是什么？它们是否可比？

**Q3.** 历史与新实验的FP/GDN运行源码、Kernel、数值设置有哪些已经确认的不同？

**Q4.** 新实验FP从13.38表面下降到7.93，最主要的已验证解释是什么？

**Q5.** deterministic/compensated路径是否真的导致Decode减速？有什么直接或间接证据？

**Q6.** 同一3090、同一输入和同一窗口下，旧runtime与新runtime分别是多少token/s？

**Q7.** 当前吞吐差异有多少能够解释，多少仍属于UNKNOWN？不要将不具独占性的时间范围强行拆成百分比归因。

**Q8.** 后续究竟应该：

- 保留当前速度并修正历史对照口径；
- 优化当前确定性主干的CPU/Kernel发射；
- 检查具体GDN Kernel；
- 还是不需要进行新的系统优化？

最后一问必须根据证据作出判断，而不是预设CUDA Graph是答案。
