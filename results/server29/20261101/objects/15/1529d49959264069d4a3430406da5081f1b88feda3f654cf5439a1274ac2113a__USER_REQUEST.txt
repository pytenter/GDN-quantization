## 5. 冻结Prefill与Decode量化时序

本次正式采用统一协议：

**FP Prefill → Prefill结束立即Dual-M QDQ → 每次Decode后Dual-M QDQ/writeback。**

具体执行顺序：

```text
1. 输入完整AIME26 Prompt

2. 执行原Hadamard数学下的Prefill

3. 得到Prefill KV/GDN Cache和最后位置Logits

4. 立即对所有24层GDN Recurrent State
   执行Hadamard+Dual-M所要求的
   INT8 QDQ/writeback

5. 根据Prefill Logits采样第一个生成token

6. 将第一个token输入下一次Model Forward

7. 使用已经量化写回的GDN State

8. 本次Forward后立即再次执行Dual-M QDQ/writeback

9. 根据本次Logits采样下一个token

10. 重复直至EOS或81920-token上限
```

需要特别核验：

- Prefill结束后是否确实执行一次QDQ。
- 第一次Decode是否消费Prefill末尾量化后的State。
- 每个Decode Forward后是否都执行QDQ。
- 下一次Forward是否消费上一次量化写回后的State。
- 所有24个GDN层是否全部覆盖。
- 是否存在重复QDQ、遗漏QDQ或未量化旁路。
- Attention KV Cache不能误当成GDN State进行Dual-M量化。

此协议**不等于Prefill内部每个Prompt token均执行QDQ**，必须在正式报告中清楚注明。

也必须注明它与旧版AIME的Prefill末尾不立即QDQ存在时序差异。

不能为了向历史Hadamard 41/60对齐而悄悄恢复旧时序。

- 记录Prefill后显存。
- 记录生成过程的allocated/reserved峰值。
- 观察长程Attention KV Cache增长。
- 保存实际生成长度和OOM发生位置。
- 不能擅自改成更短的max_new_tokens。
- 不能擅自启用滑动窗口、截断历史或CPU Offload。
- 不能为了防止OOM而改变GDN State数学。

在首批正式任务运行时检查显存增长趋势，若出现明确且不可恢复的系统性OOM，应保存全部证据并停止有问题的执行路径，而不是让60条任务重复失败。

如某个任务发生OOM或系统性非有限数值错误：

1. 保存当前job、GPU、token位置、显存与traceback。
2. 保留已完成的有效任务。
3. 不把该job自动记为数学答错。
4. 不悄悄改变batch、位宽或上下文协议重新运行。
5. 及时报告阻塞原因与可能需要的独立授权。
