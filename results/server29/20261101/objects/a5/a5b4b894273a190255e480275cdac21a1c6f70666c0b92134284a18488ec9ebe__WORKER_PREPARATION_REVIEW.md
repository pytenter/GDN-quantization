## 已发现并修正的问题

| 项目 | 审计中发现的真实缺口 | 审查版处理 |
|---|---|---|
| 完整缓存 | 初稿遗漏真实dict形式的GDN/conv状态 | 递归dict/list/tuple/tensor，绑定cache元数据、引用及storage别名；未知类型fail-closed |
| 首状态数学oracle | 初稿每步用实际initial_state重置参考 | FP64参考按层从token0独立carry；仍条件于实际模型激活 |
| 数学失败证据 | 初稿失败前只在内存保存误差 | 每helper落盘，首失败保存误差/bound和实际/参考raw；nonfinite先留证 |
| 归一化范围 | 仅观察实际GPU归一化不算独立验证 | 单独用FP64公式和冻结限值比较；不替换实际GPU归一化计算 |
| 状态别名 | 不同data_ptr仍可能属于重叠view | 持久GDN状态必须contiguous，完整地址区间两两无重叠 |
| raw容量 | 两次32token的GDN state本身已3GiB | 引用新plan的8GiB raw上限/10GiB空闲门禁，不能称只需2GB |
| 首fresh差异 | 只有token和SHA，无数值量化 | CPU解码首tensor/byte/element及maxabs/relative，layout和metadata分别描述 |
| JSON类型 | dict-key元数据使用tuple，JSON读回变list，会让fresh必然误FAIL | 改为list/list，加入真正JSON roundtrip一致性检查 |
| 环境检查时点 | 初稿numeric只在load前检查OLD环境 | model load后及POSTFLIGHT也检查，benchmark检查置于原计时外 |

所有问题发生并处理于CPU准备阶段，没有把工程假失败写成一次GPU数值失败。元数据tuple问题的独立复现保留于 `WORKER_METADATA_JSON_ROUNDTRIP_BUG.json`。最初fake未补齐dtype/device类型导致一次本地测试异常，作为审计工具历史保留；不属于worker或GPU失败。

## 检查的具体边界

Pinned架构 `90d92912...` 的真实GDN forward以q/k/v位置参数、g/beta/initial_state关键字参数调用helper，符合worker适配。native `l2norm` 采用call-through观察，不改实际GPU算式。数学参考携带独立CPU FP64状态，但输入来自实际模型q/k/v/g/b和实际归一化结果；另对归一化结果做FP64限值检查。这能准备一项有界GDN数学检查，不能称独立完整模型FP64 oracle。

新冻结限值为state `1e-5+1e-4*maxabs(reference)`、core `0.001+0.01*maxabs(reference)`、normalization `0.0001+0.02*maxabs(reference)`。这些是准备的新32token工程合同，不是继承旧数学PASS，也不是32K误差上界。没有执行GPU接受率或阈值拟合。

数值范围是32token（1token首prefill+31cached），不是256token逐字节资格。即使未来通过，也不能据此证明性能测量位置128..255的完整数值复现、多token prompt/native cumsum、32K/81K、INT8或AIME的科学资格。

fake验证了dict状态选择、元数据变化、循环引用、alias结构、未知字段拒绝、dict排序和JSON规范化；raw-diff验证了BF16解码、layout差异、metadata-only变化，以及signed zero的字节失败与数值差可以为0的区别。没有把signed zero假设为已知根因。

历史benchmark源码拷贝仍为 `08b62839e88fa6bb49f10388a19e152e04beb0ab36b347ffcfdf2d9259e2ff8c`。Shim只重绑定OLD源码路径/global，并在原计时外核验库与环境；原matched main的共同计数、finite门禁和计时结构保留。当前尚无本轮TPS实测。
