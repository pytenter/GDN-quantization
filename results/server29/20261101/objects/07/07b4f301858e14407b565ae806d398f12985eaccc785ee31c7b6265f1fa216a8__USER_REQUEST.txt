# Codex正式科研任务：Qwen/GDN INT8 Group64 四配置 AIME26 Seed1

## 0. 任务定义

`QWEN_GDN_GROUP64_FOUR_CODEC_AIME26_SEED1_V1`

**优先保证Group64与已经封存的Group32结果形成可信的同题比较。**

# 三、统一实现方式：只参数化Group Size

这是本轮最重要的效率原则。

**不要重写四个不同的Group64量化器。**

应当在已有已经验证的Group32数学核心上，以最小的版本化改动支持：

`group_size = 64`

四组共享相同的量化模块。

Native与H128继续使用已经验证的各自State坐标路径。

### 3.1 Symmetric INT8 G64

保留历史Sym32的所有规则：

- Signed INT8。
- 原实际编码区间。
- FP32 scale。
- 原amax规则。
- 原scale floor。
- 原FP32除法或CUDA reciprocal运算语义。
- 原rounding。
- 原clip。
- 原negative-zero flags。
- 原FP32 decode。
- 原QDQ及writeback位置。

数学示意：

\[
s_g=\frac{\max_{i\in g}|x_i|}{127}
\]

\[
q_i=\operatorname{clip}
\left(\operatorname{round}(x_i/s_g),-127,127\right)
\]

\[
\widehat x_i=s_gq_i
\]

以上只是概念公式；实际还必须保留原Canonical的零组、scale floor、负零和CUDA舍入细节。

不要将原GPU合格的除127路径擅自替换为另一种数学上看似等价、实际位级行为不同的运算。

### 3.2 Asymmetric INT8 G64

必须直接复用已合格的Asym32核心：

- Include-zero extrema。
- FP32 scale。
- UINT8 codes。
- 整数zero-point。
- 原Tensor/Tensor除255规则。
- 原RNE顺序。
- 原zero-point裁剪。
- 原int16扩宽再减zero-point。
- 原FP32 decode。

数学示意：

\[
a_g=\min(0,\min_{i\in g}x_i)
\]

\[
b_g=\max(0,\max_{i\in g}x_i)
\]

\[
s_g=\frac{b_g-a_g}{255}
\]

\[
z_g=\operatorname{clip}
\left(\operatorname{round}(-a_g/s_g),0,255\right)
\]

\[
q_i=
\operatorname{clip}
\left(\operatorname{round}(x_i/s_g)+z_g,0,255\right)
\]

\[
\widehat x_i=s_g(q_i-z_g)
\]

仍以原Asym32代码的精确数值合同为最终标准。

不能把`round(x/s)+z`与`round(x/s+z)`在实际GPU中未经验证地互换。

### 3.3 禁止的工程变化

不得为了Group64：

- 改变scale dtype。
- 修改clip规则。
- 改变量化轴。
- 修改Hadamard。
- 更换GDN递归Kernel数学。
- 更改Sampler。
- 延迟QDQ。
- 增加未量化State缓冲。
- 改成其他Runtime。
- 采用新的PBR分组。

除合法Group Size变化外，所有量化数学都应沿用原合格实现。

# 五、GPU真实Persistent QDQ资格

Qwen已有的实际状态语义是：

24个GDN层从规定首Token开始，每token更新后立即执行QDQ，然后写回State，下一token真实消费已QDQ后的State。

本任务必须保留这个合同。

流程：

```text
Previous QDQ State
        ↓
Original GDN Recurrence
        ↓
Updated State
        ↓
Sym64 / Asym64 Encode
        ↓
Decode
        ↓
Immediate Writeback
        ↓
Next Token Consumes QDQ State
```

### 必要检查

每种新配置至少完成：

1. GPU Codec微型字段核验。
2. 非AIME 32-token真实GDN Canary。
3. 非AIME 128-token真实GDN Canary。
4. 必要的512-token持续QDQ检查。
5. 全24层QDQ覆盖。
6. Prompt阶段逐tokenQDQ。
7. Decode阶段逐tokenQDQ。
8. 下一kernel真实读取量化重建State。
9. Scale、codes和zero-point有效。
10. State与Logits finite。
11. Fresh-process重复性。
12. Cache及Sampler reset。
13. EOS与Length合法终止。

短程真实next-consumption必须使用完整真实值与预期Decode结果核验，而不是仅通过指针、调用计数或Hash代替。

可以只在Canary中开启重型逐Tensor观察；正式AIME保留真实QDQ及冻结稀疏数值审计，不需要每token保存全部State。

### 关于长上下文

已有Group32完成81K上限的正式生成及相关资源验证。

仍应核验Group64实际Runtime能够容纳Prompt及81920新token，且不会发生新的显存或Cache布局问题。

但不需要重复设计完整81K State数值上界证明。

如复用已有长Context资源资格，必须明确其适用范围，并补齐Group64特有的有限资源检查。

不能把82293-slot合成Cache压力测试称为真实81K数值误差证明。

### State存储口径

本任务仍为数值persistent INT8。

原Runtime用FP32 Tensor承载已QDQ重建State，整体48MiB左右。

临时整数codes不等于已经实现物理packed INT8常驻。

不得报告未经实测的显存压缩率。

# 十一、科学分析：与Group32形成2×2×2消融

本轮最重要的价值，是与已完成Group32形成：

`Group Size × Sym/Asym × Native/H128`

三个二元因素。

## 11.1 固定Group64，观察非对称量化作用

Native：

`G64-1 - G64-0`

Hadamard：

`G64-3 - G64-2`

## 11.2 固定Group64，观察Hadamard作用

Symmetric：

`G64-2 - G64-0`

Asymmetric：

`G64-3 - G64-1`

## 11.3 固定Codec与Rotation，比较Group64和Group32

四项主比较：

| Group64 | Group32历史匹配条件 |
|---|---|
| G64-0 | Q0 |
| G64-1 | Q1 |
| G64-2 | Q2 |
| G64-3 | Q3 |

比较正确率与同题correctness flips。

例如：

\[
\Delta_{\mathrm{Asym,Native}}
=
Acc(G64\text{-}1)-Acc(Q1)
\]

\[
\Delta_{\mathrm{Asym,H}}
=
Acc(G64\text{-}3)-Acc(Q3)
\]

重点回答Asym64能否保留Asym32的25/30水平。

## 11.4 Group Size与Asymmetric之间的交互

以Native为例：

\[
I_{\mathrm{Native}}
=
[Acc(G64\text{-}1)-Acc(G64\text{-}0)]
-
[Acc(Q1)-Acc(Q0)]
\]

Hadamard同理。

这可观察Asymmetric优势是否随Group Size变化。

## 11.5 三因素交互

在同题一致、协议身份可比较的前提下，计算：

\[
I_{64}
=
[Acc(G64\text{-}3)-Acc(G64\text{-}2)]
-
[Acc(G64\text{-}1)-Acc(G64\text{-}0)]
\]

\[
I_{32}
=
[Acc(Q3)-Acc(Q2)]
-
[Acc(Q1)-Acc(Q0)]
\]

\[
I_{\mathrm{3way}}=I_{64}-I_{32}
\]

这个量描述：Hadamard与Asymmetric的交互是否随Group Size改变。

只进行探索性解释，不将差中差直接宣称为已证明的物理机制。

## 11.6 统计要求

同题配对输出：

- rescued。
