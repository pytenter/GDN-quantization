## 2. Phase 0A：完整性能调用链审计

CPU-only完成。

绘制实际运行流程：

```text
Model Forward
  ↓
Q/K Hadamard transform
  ↓
GDN recurrent state update/readout
  ↓
Dual-M row scale
  ↓
Dual-M initial column scale
  ↓
Initial INT8 levels
  ↓
Column LS fitting
  ↓
Final INT8 re-encode
  ↓
QDQ/writeback
  ↓
Next token consumes quantized state
```

这只是数学分析结构，真实代码可能已融合多个步骤。

必须从源码确认：

1. 哪些操作已有Triton/CUDA融合。
2. 哪些仍是独立PyTorch操作。
3. 每个token发生多少次CUDA kernel launch。
4. 是否出现重复State读取和写回。
5. 是否产生完整的额外FP32 State副本。
6. 是否存在 `.item()`、`.cpu()`、隐式同步。
7. 是否有Python hook或observer引起额外调用。
8. GDN update/readout是否已经和Codec部分融合。
9. 真实CUDA stream与事件依赖。
10. 是否存在不必要的重复Encode/Decode。

不得预先假设LS就是主要瓶颈。

## 4. Phase 1：仅实现一个主要等价优化候选

基于Phase 0结果决定优化什么。

按照以下优先级选择。

### 情况A：主要瓶颈是Python、Kernel Launch或重复访存

优先减少不必要的调用、同步或临时张量。

不得改变数学和QDQ时序。

如果有资格移除仅用于诊断的observer，必须验证observer ON/OFF对codes、scales、logits、写回State和下一个token完全没有影响。

仍应保留原科学协议要求的安全与有限性门禁。

不得为了测速而绕过真正的QDQ。

### 情况B：主要瓶颈是Row/Column计算与LS

实现一个最小的Fused Dual-M候选。

优先考虑：

```text
Kernel 1:
  Row statistics
  FP16 row scale

Kernel 2:
  Column initial scale
  Initial code selection
  LS numerator/denominator
  FP16 fitted column scale
  Final code selection
  QDQ/writeback
```

这仅是候选结构。

如果发现单kernel或两kernel结构不利于GPU occupancy、寄存器使用或访存合并，可以采用实测更好的最小划分。

数学定义保持：

\[
r_i=\operatorname{FP16Clamp}
\left(\sqrt{\operatorname{mean}_j |S_{ij}|}\right)
\]

\[
c_j^{(0)}=\operatorname{FP16Clamp}
\left(\max_i\frac{|S_{ij}|}{127r_i}\right)
\]

\[
z_{ij}^{(0)}
=\operatorname{RoundClampINT8}
\left(\frac{S_{ij}}{r_ic_j^{(0)}}\right)
\]

\[
c_j^{(1)}
=\operatorname{FP16Clamp}
\left(
\frac{\sum_i(r_i z_{ij}^{(0)})S_{ij}}
{\sum_i(r_i z_{ij}^{(0)})^2}
\right)
\]

\[
z_{ij}^{(1)}
=\operatorname{RoundClampINT8}
\left(\frac{S_{ij}}{r_ic_j^{(1)}}\right)
\]

以上仅是说明数学结构，实际kernel必须继承原reference所有特殊规则，包括：

- 数值floor与ceiling
- FP16 conversion
- ties/rounding
- clamp次序
- zero denominator fallback
- zero state
- finite检查
- tensor layout与stride
- dtype转换顺序

不得用fast-math近似静默改变数值结果。

不得取消LS。

不得减少原数学要求的编码步骤。

不得改变scale存储精度。

不得将row/column scale改为FP32常驻，以假装提高精度。

### 情况C：主要瓶颈来自原生GDN或模型主干

如果Codec只占额外耗时的一小部分，不要继续优化LS。

必须客观报告State-only quantization在当前batch=1 BF16模型下的加速上限。

不得为了得到正向吞吐而修改模型权重精度或GDN数学。

## 5. Phase 2：等价数值资格

这是本次最重要的验收环节。

优化候选不能仅因为运行更快就替换Reference。

必须比较：

```text
Old H_DUAL_M Reference
vs
New H_DUAL_M Optimized
```

使用完全相同的State输入及数学配置。

### Gate A：Codec parity

覆盖：

- Zero State
- Constant State
- Random State
- Real GDN State
- Outlier State
- 非连续布局
- FP16极小scale
- FP16极大scale
- signed ties
- batch=1
- 合法的其他batch配置（如果当前实现支持）

检查：

1. INT8 codes
2. FP16 row scale bit pattern
3. FP16 column scale bit pattern
4. Reconstructed QDQ state
5. finite与clipping结果
6. writeback timing
7. 原安全门禁

对于声称数学等价的优化，优先要求bytewise/bitwise exact。

不能把存在code不同的候选直接标记为EXACT。

如果因浮点归约次序产生差异，应记录首个差异位置、幅度及其传播影响，并保持候选为`NUMERICAL_NONEXACT`，不自动升级到正式生产路径。

### Gate B：真实Recurrent运行

在同样的非AIME token序列上，比较旧实现与新实现：

- 每token后的QDQ state
- 下一token实际消费的状态
- GDN关键输出
- full-model logits
- sampling前的输出
- 固定seed下生成的token序列

至少覆盖128-token，再按资源条件扩展1024或2048-token。

两臂使用各自独立state，不能通过将Reference state注入优化臂来制造一致。

### Gate C：重复性

同一合格GPU上执行fresh-process重复，核验源码、状态及必要的数值身份。

如果不能达到原冻结的确定性合同，保留实际差异，不静默修改容差或后处理codes。

原FP_NATIVE/H门禁失败继续保留，不属于本轮需要消除的差异。

## 6. Phase 3：真实加速验收

数值资格通过后才进行最终性能比较。

使用与Phase 0相同的GPU、输入序列、模型、采样/回放方式、长度与测量策略。

比较：

```text
H_DUAL_M_REFERENCE
H_DUAL_M_OPTIMIZED
```

必须同时报告：

- Codec-only速度
- Full-model decode吞吐
- 实际wall token latency
- p50/p95
- Kernel launch数量
- 峰值CUDA allocated/reserved
- 临时tensor bytes
- 实际resident state bytes
- Profiling开销

核心指标：

\[
\mathrm{Speedup}=
\frac{T_{\mathrm{Reference}}}
{T_{\mathrm{Optimized}}}
\]

`T`必须使用相同测量范围的真实wall time。

建议以**同条件完整decode吞吐提高至少10%**作为值得继续投入长程科学验证的性能目标，而不是事后挑选最有利的微基准。

低于10%时如实记录，不能宣称性能失败或修改结果，但应评估进一步复杂Kernel开发是否值得。

如果Codec microbenchmark加速明显，而完整模型几乎没有加速，也应明确报告。这可能表明主干计算或其它开销占主导。

禁止将CUDA event局部加速冒称完整推理加速。

## 7. 精度保护与后续科学边界

本任务的目标是保持原Dual-M数值不变。

因此：

- 不增加新的Rotation。
- 不改变INT8位宽。
- 不更换row/column公式。
- 不删除Column LS。
- 不增加FP16 pivots。
- 不训练参数。
- 不改变AIME采样协议。
- 不改已经封存的32K Future-KL结果。

如果得到bitwise一致的优化候选，可将其标记为：

`EQUIVALENT_CODEC_CANDIDATE`

如果模型短程数值与token序列也通过：

`SHORT_RUNTIME_PARITY_QUALIFIED`

但这仍不等于已独立确认32K和AIME准确率。

任何非exact候选只能进入未来独立科学消融，不能自动取代当前Hadamard+Dual-M正式方法。

**这次不自动运行32K Future-KL或AIME26。**

只有完成本次性能与数值资格后，才建议另行授权对最终候选进行长程功能验证。

如需之后验证AIME，应在原正式AIME运行结束、结果封存之后使用统一的30题×2seed协议，不通过少数有利样本宣称“正确率无下降”。
