# Codex科研任务：Qwen/GDN Asymmetric INT4 Group32 × Hadamard AIME26 Seed1

## 0. 任务身份

任务名称：

`QWEN_GDN_ASYM_INT4_GROUP32_AIME26_SEED1_V1`

目标模型：

**Qwen3.5-9B / GDN**

可使用算力：

**Qwen服务器上一张当前空闲的RTX3090 24GB。**

只允许使用这一张已经核验为空闲的GPU，不得占用其他GPU，也不得停止、抢占其他研究任务。

### 总目标

基于已经通过GPU数值资格的Qwen HISTORICAL_PORT和Asymmetric INT8 Group32实现，新增两种Asymmetric INT4 Group32配置：

| ID | Rotation | Quantization | Group |
|---|---|---|---|
| I4-N | Identity / Native | Asymmetric INT4 | Key Group32 |
| I4-H | Key-side H128 | Asymmetric INT4 | Key Group32 |

两种配置分别完成：

- AIME2026全部30道题。
- 固定seed=1。
- 最大81920个新生成token。
- 完整自由生成。
- 原Qwen Frozen V4评分。

共计：

**2 configs × 30 problems × 1 seed = 60条正式生成。**

本次的科学目标是判断：

1. Asymmetric INT4 Group32能否保留INT8的数学推理能力？
2. INT4情况下，Key-side Hadamard能否改善准确率？
3. 从8-bit降低到4-bit，正确率、生成长度和数值稳定性发生了什么变化？

本任务不研究训练、混合精度、Dual-M、其他Group Size或者新的Future-KL方法。

# 二、INT4数值合同

这是本任务最重要的工程工作。

## 2.1 不改变分组方向

Qwen/GDN的每个Recurrent Head维护一个Key×Value State。

本任务采用：

`State Shape = 128 × 128`

沿Key维度分组。

每个Value列的128个Key元素划分成4个连续Group，每组32元素。

禁止：

- 按Value维度错误分组。
- 跨Value列分组。
- 跨Head分组。
- 跨Layer分组。
- 把32×32 Tile误当作本次Group32。

I4-N和I4-H必须采用相同的Group定义，只允许旋转坐标不同。

## 2.2 非对称INT4定义

新增一个独立的Canonical INT4量化器。

编码范围：

\[
q \in \{0,1,\ldots,15\}
\]

使用逻辑UINT4编码，必要时可以由UINT8 Tensor承载0–15。

每Group输入为32个FP32数值。

先计算：

\[
x_{\min}=\min(0,\min_i x_i)
\]

\[
x_{\max}=\max(0,\max_i x_i)
\]

采用：

\[
s=\max\left(\frac{x_{\max}-x_{\min}}{15},s_{\min}\right)
\]

其中scale floor应根据现有Asym INT8数值合同恢复并审计，不得未经验证自行修改。

整数zero-point：

\[
z=\operatorname{clip}_{[0,15]}
\left(\operatorname{RNE}(-x_{\min}/s)\right)
\]

编码：

\[
q_i=
\operatorname{clip}_{[0,15]}
\left(
\operatorname{RNE}(x_i/s)+z
\right)
\]

解码：

\[
\hat x_i=s(q_i-z)
\]

上述公式是拟采用的数学合同。必须通过源码审计，确认它与现有Asym32的舍入和运算顺序保持相应一致；若原实现使用`round(x/s + z)`而非`round(x/s)+z`，不得假装两者在所有FP32输入上位级相同，应在冻结INT4合同前明确选择并测试。

### 固定数值属性

- FP32 scale。
- Integer zero-point。
- Include-zero min/max。
- RNE rounding。
- UINT4逻辑编码0–15。
- 显式clip。
- Decode时先进行足够宽的整数扩展，再减zero-point。
- FP32 decode。
- 无未量化State shadow。

必须保留现有Asym INT8的正常行为，不得为了实现INT4改动原INT8 Canonical AST、已有数值结果或封存源码。

新INT4作为独立版本实现。

## 2.3 必须覆盖的边界输入

至少包括：

- 全零Group。
- 全正常数Group。
- 全负数Group。
- 正负混合Group。
- 单个极大正值。
- 单个极小负值。
- 小动态范围。
- 数值恰好落在舍入中点。
- scale floor激活。

- encode后的code合法性。
- decode后的finite。
- clipping和saturation计数。
- FP32极端值与除法语义。

采用独立CPU参考和GPU实现进行严格数值核验。

对已经定义为逐字节相同的字段不能放宽阈值。

若CPU与CUDA发生数值差异，必须记录：

- 第一个真实失败Group输入。
- scale运算阶段。
- FP32除法结果。
- rounding前结果。
- zero-point。

不能通过随意更改dtype、epsilon、舍入规则或者提高阈值使测试变成PASS。

如必须修复，先定位原因，再以版本化的明确修订完成一次系统性验证，不进行无限次试错。

# 四、真实Persistent INT4 QDQ

本任务必须保持真实每token量化反馈。

对于每个GDN层：

```text
Previous QDQ State
        ↓
Native GDN Update
        ↓
Current FP32 State
        ↓
Asym INT4 Group32 Encode
        ↓
Asym INT4 Group32 Decode
        ↓
Immediate State Writeback
        ↓
Next Token Uses Decoded State
```

关键要求：

1. 从第一个需要persistent state的token开始执行QDQ。
2. 全部GDN层都参与。
3. 每token执行一次规定的量化反馈。
4. 不延迟到多个token之后再量化。
5. 不使用未量化的高精度State进行下一轮递归。
6. 不使用LeapQuant式窗口内高精度缓存。
7. QDQ后的State必须确实被下一kernel消费。

原HISTORICAL_PORT资格使用query length=1并拒绝未经资格的多token chunk。

因此，本次不得为了提高INT4速度而引入不合法的chunk Prefill或者跳过Prompt QDQ。

如果使用stepwise Prefill，必须保证Prompt与Decode整个流程数学一致。

### 关于物理INT4

本轮首先验证的是**逻辑4-bit整数QDQ科学效果**。

可以保留原FP32 QDQ重建State载体。

若codes使用UINT8承载0–15，也不称为物理4-bit packed存储。

必须在报告中区分：

- 逻辑INT4数值语义。
- 实际codes dtype。
- 实际persistent State dtype。
- 理论packed INT4容量。
- 实测GPU显存。

不要声称已有4倍或8倍实际显存压缩。

# 十二、与历史INT8 Asym32比较

如果原INT8两组已经完成30/30且协议匹配，则产生：

| Rotation | INT8 Asym32 | INT4 Asym32 |
|---|---|---|
| Native | 历史匹配结果 | I4-N |
| Key-H128 | 历史匹配结果 | I4-H |

重点比较：

### 1. Native坐标降bit

`Acc(I4-N) - Acc(INT8 Native Asym32)`

### 2. Hadamard坐标降bit

`Acc(I4-H) - Acc(INT8 H Asym32)`

### 3. INT4下Hadamard的作用

`Acc(I4-H) - Acc(I4-N)`

### 4. 旋转与位宽的交互

\[
I=
[A(I4-H)-A(I4-N)]
-
[A(I8-H)-A(I8-N)]
\]

- 独立复核。
- INT4两条件逐题配对。
